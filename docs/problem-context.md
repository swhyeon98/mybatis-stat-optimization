# 문제 상황과 프로젝트 배경

## 실무 문제

운영 중인 통계 페이지에서 응답 지연이 발생했다.
처음에는 사이트 전반의 성능 문제처럼 보였지만, MyBatis SQL 로그를 확인한 결과 특정 통계 페이지에서 `COUNT` 쿼리가 반복적으로 실행되고 있었다.

## 원인

통계표의 각 셀을 개별 `COUNT` 쿼리로 조회하는 구조였다.
행과 컬럼이 늘어날수록 SQL 실행 수가 증가했고, DB round-trip이 응답 지연의 주요 원인이 되었다.

## 반복 SQL 호출이 응답 지연으로 이어지는 이유

셀 단위 `COUNT` 방식에서는 통계표의 각 셀을 개별 SQL로 조회한다.
이 구조에서는 페이지 1회 조회 시 화면에 필요한 셀 개수만큼 SQL이 반복 실행된다.

사용자 입장에서는 통계 페이지를 한 번 조회한 것이지만, 서버 입장에서는 하나의 요청을 처리하기 위해 여러 번 DB에 접근해야 한다.

반복 SQL 호출은 다음과 같은 부담을 만든다.

* 애플리케이션과 DB 사이의 round-trip 증가
* SQL 실행을 기다리는 동안 WAS 요청 처리 스레드 점유
* DB 커넥션 사용 시간 증가
* DB가 처리해야 하는 총 SQL 수 증가
* 동시 요청 상황에서 DB CPU 사용량, 인덱스 탐색, 버퍼 풀 접근, 필요 시 I/O 비용 증가
* 일부 요청의 지연이 커지면서 p95 응답 시간 악화 가능성 증가

예를 들어 통계 페이지 요청 1건당 240회의 SQL이 실행되는 구조라면, 동시에 같은 페이지를 조회하는 요청 수가 증가할수록 DB에 전달되는 SQL 수는 빠르게 증가한다.

| 동시 페이지 요청 수 | 요청당 SQL 수 | 발생 SQL 수 |
| ----------: | --------: | -------: |
|          1건 |      240회 |     240회 |
|         10건 |      240회 |   2,400회 |
|         30건 |      240회 |   7,200회 |
|        100건 |      240회 |  24,000회 |

따라서 단일 SQL 하나의 실행 시간이 길지 않더라도, 페이지 1회 조회당 SQL 실행 수가 과도하게 많으면 전체 응답 시간이 느려질 수 있다.

## 예제화 방식

실제 업무 데이터와 화면은 공개할 수 없기 때문에, 고객 문의 처리 통계라는 가상 도메인으로 단순화했다.

실무에서는 페이지 1회 조회 시 약 240회의 SQL이 실행되는 구조가 문제였지만, 이 프로젝트에서는 8행 × 8개 수치 컬럼으로 구성된 통계표를 기준으로 문제를 단순화했다.

이를 통해 8행 × 8개 집계 수치 컬럼을 각각 개별 COUNT 쿼리로 조회할 경우, 요청 1회당 최대 64회의 SQL이 실행되는 구조를 재현했다.

## 프로젝트 목표

* 문제 구조 재현
* 실무 개선 방식에 가까운 행 단위 집계 구현
* 추가 개선 후보로 단일 집계 쿼리 구현
* 각 방식의 장단점 비교
