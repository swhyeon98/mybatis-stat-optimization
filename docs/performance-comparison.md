# Performance Comparison

## 환경

- CPU: Apple M1
- Memory: 16GB
- Java: Amazon Corretto OpenJDK 21.0.10
- Gradle: 8.14.4
- OS: macOS 15.7.2 aarch64
- MySQL: 8.0.46
- Spring Boot: 3.5.14
- 테스트 일시: 2026. 05. 14.

## 테스트 목적

이 문서는 MyBatis 기반 고객 문의 통계 화면에서 통계 처리 방식에 따라 응답 시간, SQL 실행 횟수, SQL 실행 시간, 커넥션 풀 대기 여부가 어떻게 달라지는지 비교하기 위해 작성했다.

- v1은 통계 셀마다 개별 `COUNT` 쿼리를 실행한다.
- v2는 Controller/View 구조를 개선하지만 SQL 실행 횟수는 v1과 동일하다.
- v3는 고정된 통계 컬럼을 대상으로 단일 집계 쿼리를 사용해 DB round-trip을 줄인다.
- 단일 집계 쿼리는 SQL 복잡도가 증가하므로, 실제 운영 환경에서는 통계 조건, 컬럼 변경 가능성, 데이터 크기, 인덱스 구성, 유지보수성을 함께 고려해야 한다.

## 측정 기준

- 데이터 수: 3,200건
- 테스트 시간: 각 시나리오별 30초
- 요청 간 대기 시간: `SLEEP=1`
- 첫 요청은 warm-up으로 제외했다.
- k6는 `performance/k6/stat.js` 단일 스크립트를 사용했다.
- 평균 응답 시간과 p95는 k6의 `http_req_duration` 기준이다.
- SQL 실행 수와 SQL 총 시간은 응답 헤더 `X-Perf-*` 값을 k6 custom metric으로 집계한 값이다.
- Hikari pending은 테스트 중 Actuator metrics를 1초 간격으로 수집한 뒤 최대값을 기록했다.
- 로컬 PC 환경에서 수행한 테스트이므로 절대 수치보다 v1/v2/v3 간 상대 비교를 중심으로 해석한다.

## 메모

- 첫 요청 warm-up 제외 여부: 제외

- HikariCP max pool size: 10

- 모든 시나리오에서 Hikari pending은 0이었다.

- 3,200건 기준 테스트이므로, 대용량 데이터에서의 결과는 별도 측정이 필요하다.
- 로컬 환경에서 측정한 결과이므로 단발성 지연이나 백그라운드 작업의 영향을 받을 수 있다.

## 해석

### v1과 v2 비교

v1과 v2는 모두 요청 1회당 SQL을 64회 실행했다.

v2는 Controller의 반복적인 `model.addAttribute` 호출을 제거하고, 통계 행/열을 DTO 기반 구조로 정리한 버전이다. 따라서 코드 구조와 유지보수성 측면에서는 개선이 있지만, DB 접근 횟수는 줄어들지 않는다.

측정 결과도 이 특성과 일치한다.

- VUS=1 기준 v1 평균 응답 시간은 98.10ms, v2는 85.78ms였다.
- VUS=10 기준 v1 평균 응답 시간은 96.03ms, v2는 103.39ms였다.
- 두 방식 모두 SQL 실행 수는 64회로 동일했다.

즉, v1과 v2의 응답 시간은 측정 시점에 따라 차이는 있지만 구조적으로 큰 성능 개선이라고 보기는 어렵다.

v2의 핵심 가치는 성능 최적화가 아니라, Controller/View 중복을 줄인 유지보수성 개선에 있다.

### v2와 v3 비교

v3는 `SUM(CASE WHEN ...)`과 `GROUP BY` 기반 단일 집계 쿼리로 동일한 통계 결과를 만든다.

v1/v2는 요청 1회마다 SQL을 64회 실행하지만, v3는 SQL을 1회만 실행한다. 이 차이는 응답 시간에서도 뚜렷하게 나타났다.

- VUS=1 기준 v2 평균 응답 시간은 85.78ms, v3는 19.38ms였다.
- VUS=10 기준 v2 평균 응답 시간은 103.39ms, v3는 21.17ms였다.
- p95 기준으로도 v1/v2는 약 110~164ms 수준이었지만, v3는 약 25~31ms 수준이었다.

이번 측정에서는 데이터 수가 3,200건으로 크지 않았음에도, DB round-trip을 줄인 v3가 더 낮은 응답 시간을 보였다.

### SQL 실행 시간 관점

SQL 총 시간 평균을 보면 v1/v2와 v3의 차이가 더 명확하다.

- VUS=1 기준 v1의 SQL 총 시간 평균은 90.14ms, v2는 75.71ms, v3는 11.10ms였다.
- VUS=10 기준 v1의 SQL 총 시간 평균은 89.51ms, v2는 96.09ms, v3는 13.74ms였다.
- v1/v2의 SQL 실행 수는 64회로 고정되었고, v3는 1회로 고정되었다.

따라서 이번 테스트에서 응답 시간 개선의 주된 원인은 SQL 실행 횟수와 DB round-trip 감소로 볼 수 있다.

### Hikari pending 관점

모든 시나리오에서 Hikari pending 최대값은 0이었다.

이는 테스트 중 커넥션 풀에서 커넥션을 얻기 위해 대기한 요청이 관찰되지 않았다는 의미다.

따라서 이번 측정에서는 응답 시간 차이를 커넥션 풀 대기 때문이라고 보기는 어렵다.

이번 결과는 커넥션 풀 병목보다는 다음 요인의 영향으로 해석하는 것이 적절하다.

- SQL 실행 횟수 차이
- DB round-trip 횟수 차이
- 여러 개의 COUNT 쿼리를 반복 실행하는 구조와 단일 집계 쿼리 구조의 차이

다만 VUS=10, SLEEP=1 조건은 비교적 완만한 부하 조건이다. 더 높은 VUS, 더 짧은 SLEEP, 더 큰 데이터 수에서는 Hikari pending이나 DB 부하가 다르게 나타날 수 있다.

### 운영 관점에서의 주의점

이번 테스트에서 v3가 가장 낮은 응답 시간을 보였지만, 이것이 모든 통계 화면에서 단일 집계 쿼리가 항상 정답이라는 의미는 아니다.

v3 방식은 다음 장점이 있다.

- SQL 실행 횟수 감소
- DB round-trip 감소
- 고정된 통계 컬럼에서 빠른 조회 가능

하지만 다음 단점도 있다.

- SQL이 길어진다.
- 통계 규칙이 SQL 안에 강하게 포함된다.
- 통계 컬럼이나 상태 코드가 자주 바뀌면 유지보수가 어려워질 수 있다.
- 동적인 통계 조건이 많아지면 `GROUP BY category, status` 후 Java 피벗 방식이나 목적별 다중 집계 쿼리가 더 적합할 수 있다.

## 결론

이번 테스트에서 확인한 내용은 다음과 같다.

- v2는 코드 구조 개선에는 의미가 있지만, SQL 실행 횟수를 줄이지 않기 때문에 성능 개선 효과는 제한적이다.
- v3는 고정 컬럼 통계표에서 SQL 실행 수를 64회에서 1회로 줄였고, 응답 시간도 크게 낮아졌다.
- 이번 테스트에서는 Hikari pending이 발생하지 않았으므로, 성능 차이는 커넥션 풀 대기보다 SQL 실행 횟수와 DB round-trip 차이의 영향으로 해석하는 것이 적절하다.
- 성능 개선의 핵심은 단순히 Controller 코드를 정리하는 것이 아니라, DB 접근 구조를 바꾸는 데 있었다.
- 다만 단일 집계 쿼리는 SQL 복잡도가 증가하므로, 실제 서비스에서는 통계 화면의 변경 가능성, 실시간성, 데이터 크기, 인덱스 구성, 유지보수성을 함께 고려해야 한다.

이 프로젝트에서 v3는 “항상 정답인 방식”이 아니라, 고정된 통계 컬럼을 가진 화면에서 선택할 수 있는 개선안 중 하나로 볼 수 있다.

추가 측정 후보

이번 문서에서는 3,200건 데이터 기준의 기본 비교만 기록했다.

추가로 다음 조건을 측정하면 더 깊은 분석이 가능하다.

| 시나리오                                       | 가정 상황                                           | 목적                                  |
| ------------------------------------------ | ----------------------------------------------- | ----------------------------------- |
| 100,000건 / VUS=10 / SLEEP=1                | 데이터가 증가한 상태에서 여러 관리자가 통계 화면을 조회한다               | 데이터 수 증가에 따른 응답 시간, SQL 실행 시간 차이 확인 |
| VUS=30 / SLEEP=0.5 / DURATION=1m           | 여러 사용자가 짧은 간격으로 필터 변경, 새로고침, 재조회한다              | 현실적인 고부하 상황에서 v1/v2/v3 차이 확인        |
| VUS=50 / SLEEP=0 / DURATION=1m             | 사용자가 미친 듯이 새로고침하거나, 브라우저 자동 새로고침/스크립트성 요청이 발생한다 | 구조적 한계를 보기 위한 stress test           |
| VUS=50 / SLEEP=0 / Hikari max pool size 축소 | 동시 요청은 많은데 DB 커넥션 풀 크기가 충분하지 않다                 | 커넥션 풀 제한 상황에서 pending 발생 여부 확인      |
| 인덱스 변경 전후 비교                               | 데이터가 많아졌을 때 적절한 인덱스가 있는 경우와 없는 경우를 비교한다         | rows examined와 SQL 실행 계획 차이 확인      |
| 캐시 적용 전후 비교                                | 같은 조건의 통계 화면을 반복 조회한다                           | 반복 조회에서 DB 부하를 줄일 수 있는지 확인          |
| 요약 테이블 적용 비교                               | 실시간 집계 대신 미리 계산된 통계 테이블을 조회한다                   | 대시보드성 통계에서 조회 성능과 실시간성 trade-off 확인 |

이번 기본 테스트에서는 Hikari pending이 발생하지 않았지만, 더 높은 동시 요청 수와 짧은 요청 간격에서는 커넥션 풀 대기, DB CPU 사용량, 쿼리 실행 계획 차이가 더 크게 드러날 수 있다. 따라서 추가 측정에서는 단순 응답 시간뿐 아니라 Hikari pending, active connection, SQL 실행 시간, rows examined를 함께 확인할 필요가 있다.
