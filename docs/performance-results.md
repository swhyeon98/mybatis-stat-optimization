# 성능 측정 결과

## 1. 결과 요약

고객 문의 통계 페이지 예제를 기준으로 v1, v2, v3의 성능을 비교했다.

비교 대상은 다음과 같다.

| 버전 | 방식             | 요청당 SQL 실행 수 |
| -- | -------------- | -----------: |
| v1 | 셀 단위 COUNT 방식  |          64회 |
| v2 | 행 단위 집계 방식     |           8회 |
| v3 | 전체 단일 집계 쿼리 방식 |           1회 |

측정 결과, 요청당 SQL 실행 수가 줄어들수록 서버 처리 시간과 SQL 총 실행 시간이 함께 감소했다.

고정된 시간 동안 반복 요청을 수행한 결과, 빠른 버전일수록 더 많은 요청을 완료했다.
따라서 `완료 요청 수`는 동일 요청 수 비교가 아니라, 같은 시간 동안 각 버전이 처리한 요청량을 의미한다.

## 8. 결과 해석

### 8.1 완료 요청 수가 다른 이유

이 테스트는 각 버전에 동일한 요청 수를 보내는 방식이 아니라, 정해진 시간 동안 각 VU가 요청을 반복하는 방식으로 수행했다.

따라서 요청 처리 시간이 짧은 버전일수록 같은 시간 안에 더 많은 요청을 완료할 수 있다.

예를 들어 3,200건 / VUS 30 조건에서 완료 요청 수는 다음과 같다.

| 버전 | 서버 평균(ms) | 완료 요청 수 |
| -- | --------: | ------: |
| v1 |    103.59 |   2,996 |
| v2 |     37.22 |   3,346 |
| v3 |     14.35 |   3,480 |

v3는 요청당 처리 시간이 가장 짧기 때문에 가장 많은 요청을 완료했다.
반대로 v1은 요청당 처리 시간이 가장 길기 때문에 같은 시간 동안 완료한 요청 수가 가장 적었다.

완료 요청 수는 테스트 기간 동안의 처리량을 보여주는 보조 지표로 해석한다.

### 8.2 요청당 SQL 실행 수 감소 효과

v1은 요청 1회당 SQL을 64회 실행한다.
v2는 요청 1회당 SQL 실행 수를 8회로 줄였고, v3는 1회로 줄였다.

이 차이는 총 SQL 수에서 크게 드러난다.

3,200건 / VUS 30 조건에서 총 SQL 수는 다음과 같았다.

| 버전 | 완료 요청 수 | 요청당 SQL 수 | 총 SQL 수(측정 기간) |
| -- | ------: | --------: | -------------: |
| v1 |   2,996 |        64 |        191,744 |
| v2 |   3,346 |         8 |         26,768 |
| v3 |   3,480 |         1 |          3,480 |

v1은 완료 요청 수가 가장 적었음에도, 측정 기간 동안 발생한 총 SQL 수는 가장 많았다.
v3는 가장 많은 요청을 처리했지만, 총 SQL 수는 가장 적었다.

이는 셀 단위 COUNT 구조가 동시 요청 상황에서 DB에 전달되는 SQL 수를 크게 증가시킨다는 것을 보여준다.

### 8.3 서버 처리 시간과 SQL 총 실행 시간

3,200건 / VUS 30 조건에서 서버 평균 처리 시간은 다음과 같이 측정되었다.

| 버전 | 서버 평균(ms) | 서버 p95(ms) | SQL 평균(ms) | SQL p95(ms) |
| -- | --------: | ---------: | ---------: | ----------: |
| v1 |    103.59 |     179.00 |     100.01 |      175.00 |
| v2 |     37.22 |      58.00 |      32.72 |       53.00 |
| v3 |     14.35 |      26.00 |      10.26 |       20.00 |

요청당 SQL 실행 수가 줄어들면서 서버 처리 시간과 SQL 총 실행 시간이 함께 감소했다.

### 8.4 HikariCP pending connection

동시 요청 시나리오에서는 HikariCP pending connection도 차이를 보였다.

|   데이터 수 | VUS | 버전 | Hikari pending max | Hikari active max |
| ------: | --: | -- | -----------------: | ----------------: |
|   3,200 |  30 | v1 |                 20 |                10 |
|   3,200 |  30 | v2 |                  7 |                10 |
|   3,200 |  30 | v3 |                  0 |                 0 |
| 100,000 |  30 | v1 |                 12 |                10 |
| 100,000 |  30 | v2 |                  6 |                10 |
| 100,000 |  30 | v3 |                  1 |                 4 |

v1과 v2에서는 active connection이 최대 10까지 사용되었고, pending connection도 발생했다.
특히 v1은 3,200건 / VUS 30 조건에서 pending max가 20까지 증가했다.

이는 반복 SQL 호출 구조가 동시 요청 상황에서 커넥션 풀 대기까지 유발할 수 있음을 보여준다.

### 8.5 데이터 수 증가에 따른 변화

3,200건과 100,000건 모두에서 v1, v2, v3의 상대적인 차이는 유사하게 나타났다.

100,000건 / VUS 30 조건에서도 v1은 요청당 SQL 64회로 인해 총 SQL 수와 서버 처리 시간이 가장 높았다.
v2는 SQL 실행 수를 8회로 줄이며 v1 대비 서버 평균 처리 시간이 약 68.5% 감소했다.
v3는 SQL 실행 수를 1회로 줄이며 v1 대비 서버 평균 처리 시간이 약 88.4% 감소했다.

## 9. 결론

셀 단위 COUNT 방식은 구현이 단순하지만, 통계표의 셀 수가 늘어날수록 요청당 SQL 실행 수가 증가한다.
사용자 입장에서는 페이지를 한 번 조회한 것이지만, 서버 입장에서는 하나의 요청을 처리하기 위해 다수의 SQL을 반복 실행하게 된다.

이번 측정에서 v1은 요청당 SQL을 64회 실행했고, 동시 요청 상황에서 가장 높은 서버 처리 시간과 SQL 총 실행 시간을 보였다.
또한 HikariCP pending connection도 가장 크게 발생했다.

v2는 요청당 SQL 실행 수를 8회로 줄이면서 서버 처리 시간과 SQL 총 실행 시간을 크게 낮췄다.
기존 화면의 행 구조를 유지하면서 개선할 수 있다는 점에서 실무 적용에 가까운 절충안이다.

v3는 요청당 SQL 실행 수를 1회로 줄여 가장 좋은 성능을 보였다.
다만 전체 통계 규칙이 하나의 SQL에 집중되므로, 통계 조건이 복잡하거나 자주 변경되는 화면에서는 유지보수성을 함께 고려해야 한다.

이 프로젝트의 핵심은 통계 쿼리를 무조건 하나로 줄이는 것이 아니라, 반복 SQL 호출 구조가 응답 지연을 만들 수 있음을 확인하고 상황에 맞는 집계 단위를 선택하는 것이다.
